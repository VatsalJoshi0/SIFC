1. Introduction and Scope

This document describes how VAI will be built. It translates the requirements in the PRD into system
components, data structures, interfaces, formulas and operational practices. Where the PRD states a
product rule, this TRD states the exact implementation. Requirement IDs such as FR-A2 refer to the PRD.

The prototype is a complete, runnable system on dummy data. Every external dependency (OTP
delivery, vehicle registry, challan source, insurers, PUC centres and payment gateway) is behind an
adapter interface with a simulated implementation. Replacing a simulated adapter with a live one must
not require changes to the business logic, the frontend or the database schema.

2. System Architecture

VAI follows a modular monolith architecture for the prototype and Phase 2. Modules have clear
boundaries and communicate through service interfaces, so any module can be extracted into its own
service later without rewriting the others. Background work such as nightly score recalculation runs in a
separate worker process that shares the same codebase.

4.3 State and Data Handling

Server data (vehicles, challans, scores, transactions) lives in TanStack Query with stale times of 60
seconds for scores and 5 minutes for reference data such as reward tables. Mutations invalidate the
relevant query keys. Session state, which holds only the masked user summary and token expiry, lives
in a Zustand store. Access tokens are kept in memory and refresh tokens are in an HttpOnly, Secure,
SameSite=Strict cookie. The frontend never writes sensitive values to localStorage or sessionStorage.

4.4 Score Meter Specification

The circular meter maps score 500 to 900 onto a 270-degree arc. The arc colour changes by category:
amber for Fair, teal for Good and green for Very Good. Each category band is marked on the arc at 650
and 750. The numeric value is shown in the centre with its category label beneath it. The meter has an
accessible text equivalent, for example 'VAI Score 714, Good category, 36 points to Very Good', exposed
through an aria-label and a visually hidden paragraph.

4.5 Responsive Breakpoints

Layouts are designed mobile first with breakpoints at 640px (sm), 768px (md), 1024px (lg) and 1280px
(xl). Tables switch to stacked cards below 768px. Navigation becomes a bottom bar on mobile and a left
sidebar from 1024px upward. Safe-area insets are respected on iOS devices.

5.2 Request Lifecycle

Each request receives a request ID at the gateway. Middleware runs in this order: request ID, structured
logging context, security headers, CORS check, body size limit (100 KB), rate limiting, token verification,
role check, schema validation, controller, service, repository, response envelope. Services contain
business rules and never read HTTP objects. Repositories contain query code and never contain
business rules. This separation keeps the scoring engine testable as pure functions.

5.3 Configuration Management

Scoring weights, reward percentages and fee options are stored as versioned configuration rows, not in
code. Each row has an effective-from timestamp. A calculation always uses the configuration version
effective at the time of the event, so historical scores and transactions can be explained even after the
rules change. Configuration changes are written to the audit log in the same database transaction as the
change.

holding paise. Enumerated values are implemented as PostgreSQL enum types or as CHECK constraints.

6.3 Relationships and Constraints

Deleting a user is a soft operation: status becomes CLOSED and personal fields are anonymised after
the retention period, while ledger, transaction and audit rows remain for their legal retention period.
Foreign keys to users and vehicles use RESTRICT so that orphaned financial records cannot exist.
Transactions reference a vehicle and a provider at creation time; later changes to the vehicle do not
alter historical transactions because amounts are stored, not recomputed.

7.6 Pagination, Filtering and Sorting

sort=challan_date:desc, with a whitelist of allowed fields.

8.3 Token Handling

Refresh tokens are rotated on every use. The server stores a SHA-256 hash of each refresh token
together with a family ID. If a refresh token that has already been rotated is presented, the entire family
is revoked and the user must log in again, which limits the damage from a stolen token. Access tokens
carry userId, role and an expiry; they contain no PAN or mobile number.

9. VAI Scoring Engine Design

The scoring engine is a set of pure functions. Given a user's confirmed records, the current date and the
active configuration, it returns a score and a list of ledger entries. It does not read or write the database.
The worker loads inputs, calls the engine, and writes results in a single transaction. Because the engine
is pure, it is tested exhaustively with unit and property-based tests.

9.4 Decay and Recovery

Recovery happens through two mechanisms. The first is decay: each violation's influence falls by half
every 365 days, so a violation from three years ago contributes about 12.5% of its original penalty. The
second is the streak: every violation-free day counts toward the streak bonus. Together, they mean a
user with one serious violation can recover the full range of a Good score within a year of clean driving,
without the violation being erased from the ledger.

9.7 Pseudocode

function computeScore(user, challans, vehicles, licence, today, cfg):
    ledger = []
    confirmed = [c for c in challans if c.status in (PAID, UNPAID)]

    V = 0
    for c in confirmed:
        age = days_between(c.challan_date, today)
        contribution = -cfg.W[c.severity] * 0.5 ** (age / cfg.half_life_days)
        V += contribution
        ledger.append(entry(VIOLATION, "V", "VIO_" + c.severity, c.challan_id, contribution))
    V = max(cfg.v_cap, V)

    RP = repeat_penalty(confirmed, today, cfg)
    P = payment_component(challans, today, cfg)
    D = streak_bonus(confirmed, today, cfg)
    C = vehicle_component(vehicles, licence, today, cfg)

    raw = cfg.base + V + RP + P + D + C
    score = clamp(round(raw), 500, 900)

    previous = last_score(user)
    if abs(score - previous) > cfg.monthly_move_limit:
        score = previous + sign(score - previous) * cfg.monthly_move_limit
        ledger.append(entry(CAP_ADJ, "-", "MOVE_LIMIT", config_ref(cfg), ...))

    persist_ledger_and_score_in_one_transaction(user, score, raw, ledger)
    return score

11.2 Fee Calculation

The platform fee is computed on the original amount before discount. The fee rate comes from the

11.3 Refunds

A refund reverses the transaction in full or in part. For a full refund, the platform fee is also reversed. For
a partial refund, the fee reversal is proportional to the refunded share of the base amount, rounded
half-up. Refund rows are separate records linked to the original transaction; the original row is never
edited except for its status and updated_at. Refunds are restricted to SUPER_ADMIN and require a
reason code recorded in the audit log.

11.4 Idempotency

Every POST to /transactions requires an Idempotency-Key header. The server stores the key with the
response for 24 hours, and a repeated request with the same key returns the stored response without
creating a second transaction. This protects against double charges caused by network retries.

12.4 Privacy and Consent

Consent is captured in a dedicated step before the dashboard is shown. Each consent purpose (identity

pseudonymised data. Data retention and erasure follow the Digital Personal Data Protection Act, 2023
and the rules that apply to each data category once the legal review is complete.

16.2 Strategies

The API is stateless, so instances scale horizontally behind a load balancer. Score reads are served from
Redis with a five-minute TTL and invalidated on recalculation. Challan and transaction lists use indexed
cursor pagination, which keeps query cost stable as history grows. Scoring is performed asynchronously,
so a large challan import never blocks a dashboard request. Reporting queries run against a read replica
to protect transactional performance. Large tables such as the audit log and score ledger are partitioned
by month once they exceed the pilot size.

16.3 Capacity Assumptions

Each active user generates on average 40 API calls per session. Each challan event triggers one scoring
job taking under 50 milliseconds of CPU for a typical user with up to 200 records. A single worker
process can therefore process more than 1,000 user recalculations per second, and the nightly batch for
one million users completes well within its window with a small worker pool.

17.4 Failure Handling

Adapter calls use timeouts of 5 seconds and retries with exponential backoff and jitter, limited to three
attempts, and only for idempotent operations. A circuit breaker opens after five consecutive failures and
returns ADAPTER_UNAVAILABLE for 60 seconds. Background jobs are idempotent and keyed by user and
configuration version, so a retried job produces the same ledger entries and does not duplicate them.
Dead-letter queues hold jobs that fail five times and are visible in the admin dashboard.

18. Dummy Dataset Architecture

The prototype dataset is generated by a seed script that writes the ten profiles below into the same
schema used in production. Every record carries is_dummy = true. The reset operation refuses to delete
any row where is_dummy is false, so it cannot affect real data even if run by mistake. The seed is
deterministic: the same seed value produces the same records and the same expected scores, which is
essential for golden tests.

18.3 Interconnection Rules

Every challan references one user and one vehicle, and the vehicle must belong to the same user. Every
transaction references a user, a vehicle and a provider that exists. Every ledger entry references a
configuration version that exists. The seed script validates these rules before committing and aborts if
any rule fails. Dataset regeneration is available to SUPER_ADMIN from the admin dashboard, and each
regeneration is recorded in the audit log.
